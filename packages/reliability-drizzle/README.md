# Reliability Drizzle

Durable PostgreSQL, SQLite and Turso Outbox/Inbox stores. PostgreSQL claims use `FOR UPDATE SKIP LOCKED`; SQLite/Turso use one `UPDATE ... RETURNING` statement (serialize write transactions under contention). Pass the current Drizzle transaction to `appendWith(tx, envelope, { availableAt })` to bind an optionally scheduled outbox append to the business transaction. When using `@nuxt-laravelize/database`, `appendIn(unitOfWork, envelope, options)` uses that unit of work's exact transaction session; the existing `append` and `appendWith` APIs remain available.

`availableAt` controls the earliest claim time independently from the immutable envelope `occurredAt`. Duplicate IDs are accepted only when both the normalized envelope and availability are identical; conflicting reuse throws `OutboxMessageConflictError`.

Apply the dialect-specific append-availability migration (`0002` for PostgreSQL or `0003` for SQLite/Turso) after the original table migration. The immutable `append_available_at` column preserves duplicate identity when mutable `available_at` advances during retries.

Then apply the terminal-time migration (`0004` for PostgreSQL or `0005` for SQLite/Turso). `delivered()` and `dead()` record authoritative `terminal_at`; migrated legacy dead rows remain null, are excluded from lists, and direct management returns `DeadLetterUnmanagedLegacyError`. Administrators must either leave them unmanaged or backfill from independently verified source evidence in an explicit migration. Never substitute `created_at`, migration time, or another fabricated timestamp. `prune()` deletes at most `limit` rows matching namespace, terminal state, strict cutoff, and optional message types. Run bounded passes from cron or a scheduler.

Apply management migration `0006` (PostgreSQL) or `0007` (SQLite/Turso), then receipt migration `0008` (PostgreSQL) or `0009` (SQLite/Turso), before constructing `DrizzleReliabilityDeadLetterAdapter`. Migration files are package-resolvable as `@nuxt-laravelize/reliability-drizzle/migrations/<file>`. Retry/discard reserves a globally unique operation ID before one state/disposition/revision CAS. SHA-256 fingerprints include ordered action/key/revision/availability/reason fields; reason plaintext is not stored. Row operation fields are reconciliation markers only. Receipts survive message deletion because there is no cascading foreign key, and need a separately configured, evidence-aware retention process; this package does not automatically prune them or claim full attempt history. Pending operations without a matching row marker are reported ambiguous and never rerun.

Apply generalization migration `0010` (PostgreSQL) or `0011` (SQLite/Turso) before using `DrizzleDeadLetterOperationStore` with BullMQ or another external adapter. The store implements atomic operation-ID reservation and terminal compare-and-set finalization, preserves pending receipts, and round-trips opaque text revisions. A pending receipt is deliberately never reclaimed: adapters must report an ambiguous outcome rather than risk re-executing an external mutation.

Dead pruning requires `allowDeadEvidenceDeletion`; it deletes only logically discarded dead rows by default. Deleting active dead evidence additionally requires the explicit emergency `allowActiveDeadEvidenceDeletion` override.
