# @nuxt-laravelize/scheduler-nuxt

Opt-in scheduler module and execution runtime for Nuxt `>=4.4.5 <5` and its managed Nitro 2 version.

Use `CacheLockSchedulerLockProvider` from `@nuxt-laravelize/scheduler-nuxt/cache-lock` with a `DistributedCache` such as `RedisCache` for `onOneServer()` tasks. Every lock-backed runner must configure a stable, application-and-environment-specific `namespace`. `onOneServer()` renews its owner-atomic occurrence claim while work runs, releases caught failures for retry, and owner-atomically resets the full `occurrenceRetentionSeconds` window after success. A process crash leaves the claim until its TTL recovers it. Configure retention to cover both maximum execution time and the provider replay window. `withoutOverlapping()` uses a separate owner-atomic lease that renews while work runs, releases only for its current owner, exposes an abort signal after detected loss, and rejects completion after ownership loss. Redis/Valkey locks do not provide monotonic fencing across failover.

Scheduler delivery is at least once around ambiguous application or cleanup failures. Operations, queue dispatchers, and hooks must use a stable occurrence-based idempotency key, and durable writes should use a database-supported fencing token where duplicate effects are unacceptable. The runtime signal is cooperative and cannot undo external effects already committed by a stale handler.

Provider trigger generation is owned by Nitro. Standard Nuxt/Nitro 2 task invocations do not propagate Cloudflare or Vercel scheduled-event timestamps, so module-generated wrappers always use an advancing wall clock. Only the low-level `createGeneratedSchedulerTask(..., { timestampSource: 'event' })` API may opt into an explicitly supplied immutable occurrence timestamp. The standalone Cloudflare adapter accepts `ScheduledController.scheduledTime`. For Vercel production deployments, configure a strong `CRON_SECRET`; Nitro sends and validates it for generated cron endpoints. Do not expose Nitro's development task endpoints in production or invoke `runTask()` from an unauthenticated route.
