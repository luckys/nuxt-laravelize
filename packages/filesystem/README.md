# @nuxt-laravelize/filesystem

Portable filesystem disks, capability contracts, secure wrappers, an in-memory test driver, and a root-confined local Node adapter for Nuxt Laravelize.

The stable `Filesystem` API remains byte-oriented. Optional features are separate capability interfaces with fail-closed guards: temporary URLs, direct-upload issue/confirmation, visibility, SHA-256 checksums, streams, and multipart lifecycle. Unsupported disks do not fabricate these methods.

`scopedFilesystem()` confines base and optional operations below one normalized prefix. `readOnlyFilesystem()` rejects base mutations and omits optional mutation capabilities. Mutable `ReadFallbackFilesystem` requires an explicit async `FilesystemTombstoneStore`; production must provide a durable, shared implementation scoped to that logical primary/fallback pair. Tombstones are monotonic authoritative deletion history: delete records before primary removal; a non-same-path move creates the primary destination, records the source tombstone, then removes the primary source. Writes, copies, and moves never clear tombstones. A failed destination creation leaves the source visible and untombstoned. Move compatibility semantics are non-atomic: a crash or source-delete failure after destination creation can leave both primary objects. Concurrent source writers require external serialization or provider fencing because the portable contract has no conditional move. A current primary always wins and remains visible; when it is absent, the tombstone permanently suppresses stale fallback data. Fallback reads recheck authoritative tombstones after the fallback operation, while `list()` intentionally keeps snapshot semantics. Compaction is an explicit administrative operation only after verifying fallback deletion or retention completion and is intentionally absent from this API. Plan storage growth, retention, backup, and monitoring. `InMemoryFilesystemTombstoneStore` is solely for tests/development; there is no unsafe default. Only use a trusted, committed replica as fallback.

`quarantineFilesystem()` exposes an explicit staging disk plus `release()` and `reject()`. It does not scan files. `release()` requires trusted accepted scan evidence containing the normalized quarantine path and exact SHA-256. It reads one byte snapshot, verifies that snapshot, and writes those exact bytes while retaining the quarantine source in every successful case; a concurrent replacement is never promoted or deleted. Produce evidence in a trusted scanner/workflow and never accept it from an untrusted client. Cleanup is a separate `reject()` or provider-lifecycle action only after the caller establishes an immutable path/version; `release()` deliberately performs no read-then-delete because the portable `Filesystem` contract has no conditional-delete/version primitive.

The Node `LocalFilesystem` supports native streams, SHA-256 checksums, and private/public file modes (`0600`/`0644`). Its root must be exclusively controlled by the application; the pre-operation symlink checks are not a hostile same-host sandbox.
